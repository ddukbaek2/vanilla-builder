# 00. 프로젝트 개요 — vanilla-builder

작성일: 2026-09-29
상태: 초안 (미확정 항목 확인 대기)

## 1. 목적과 배경

작업 PC 에서 프로젝트의 웹 빌드 결과물과 **빌드 명세 파일**을 이 서버에 넘기면, 서버가 명세대로 macOS/iOS 앱을 빌드하고 산출물을 URL 로 내려받게 해주는 **원격 빌드 서버 애플리케이션**을 만든다.

**성격:** GitHub Actions 의 플랫폼 빌드 액션과 같은 일을 하되, 저장소를 쓰지 않고 파일을 직접 받는다. Jenkins 처럼 저장소에서 내려받아 출발하는 중앙 자동화 서버가 아니라, **수동 빌드를 대신해 주는 원격 빌더**다. 그래서 잡/파이프라인 같은 특별한 셋팅이 없다.

**비전 (2026-09-30 확정):**
- vanilla-builder 는 **어느 데스크톱 OS(macOS, Windows, Linux)에서나 도는 하나의 앱**이다. 이 앱을 실행한 머신이 곧 **빌드 노드**다. 지금 macOS 에서만 도는 것은 첫 기준(iOS/macOS 빌드에 Xcode 가 필요)일 뿐이며, macOS 전용이 목적이 아니다.
- 사용자도 어느 OS 에서든 같은 앱으로 보내고 받는다. 클라이언트와 서버가 다른 프로그램이 아니다.
- **노드끼리 통신한다.** 내 노드가 만들 수 없는 대상(예: Windows 노드에 들어온 iOS 빌드)은 접근 가능한 원격 노드에 넘겨 빌드하고 결과를 받아온다. 내 노드에서 직접 패키징한 것을 원격 노드를 거쳐 다시 빌드시킬 수도 있다.
- 따라서 방향은 Jenkins 와 다르다. 중앙 서버 하나가 아니라 **서로 연결된 빌드 노드들**이다.
- **서버와 클라이언트는 사실상 하나의 앱이다.** 설치하면 기본으로는 빌드를 받지 않고, 메뉴 막대(또는 웹 설정)의 "이 PC 에서 빌드 허용" 을 켠 PC 만 빌드 노드가 된다. (기본 꺼짐)

**로드맵:**
1. (현재) macOS 노드: macOS·iOS 빌드, 큐, 현황 페이지, 클라이언트 도구
2. Windows / Linux 노드: 같은 코드가 그 OS 에서 돌고, 그 OS 가 만들 수 있는 대상(Windows, Linux, Android, Web)을 빌드
3. 노드 연결: 노드 등록/발견, 대상별로 어느 노드가 만들 수 있는지 광고, 원격 노드로 작업 위임과 결과 회수
4. 릴레이: 로컬에서 패키징 → 원격 노드에서 빌드 → 결과를 다시 로컬로

**배경:** 사용자의 주 작업 PC 는 **Windows** 다. iOS 와 macOS 빌드는 Xcode 때문에 Mac 이 필요해서, 지금까지는 빌드할 때마다 Mac 에서 git pull 을 받고 직접 빌드를 돌려야 했다. 이 수고를 없애기 위해 Windows PC 에서 프로젝트를 Mac 으로 넘기고, Mac 이 빌드해서 산출물을 돌려주는 서버를 만든다.

**사용 시나리오:** 작업 PC 에서 AI(예: Claude Code)에게 "맥 빌드해줘" 라고 말하면, AI 가 프로젝트 파일 전체와 빌드 명세 파일을 이 서버에 전달한다. 서버는 명세대로 빌드하고, 완료되면 AI 가 다운로드 URL 로 산출물을 받아 온다.

**우선순위:** Mac 이 아니면 만들 수 없는 **iOS 와 macOS 빌드가 1순위**다. Windows, Linux, Android, Web 은 Windows PC 에서도 가능하지만 같은 서버에서 한 번에 뽑을 수 있게 한다.

## 2. 확정 사항 (사용자 지시)

- Git 등 소스 저장소 연동은 하지 않는다. 클라이언트가 프로젝트 파일을 직접 서버에 넘긴다.
- **주 클라이언트는 작업 PC 에서 동작하는 AI(또는 스크립트)** 이며, HTTP 로 서버에 접근한다. 브라우저 페이지는 진행 현황 확인용이다.
- 클라이언트는 프로젝트 파일과 함께 **빌드 명세 파일**을 넘긴다. 프로젝트 전달 형식은 압축이든 개별 파일이든 무방하다.
- 서버는 넘겨받은 프로젝트를 **명세대로 빌드**하고, 산출물은 **클라이언트가 URL 로 다운로드**한다. 결과 폴더 지정은 하지 않는다.
- 대상 프로젝트는 우선 **scramble-heroes**(게임)와 **my-diabetes-notes**(앱) 두 개다. 둘 다 사용자의 템플릿 기반 JavaScript 프로젝트다.
- **Capacitor/Electron 껍데기는 이 서버가 생성한다.** 프로젝트마다 `platforms/` 아래에 두던 플랫폼 구성과 빌드 스크립트(`tools/manifest.cjs`, `platforms/*/tools/*.cjs`)의 역할을 이 서버가 대신한다.
- 빌드 산출물 대상 플랫폼은 **6종**이다: macOS, Windows, Linux, Android, iOS, Web.
- 빌드 노드는 어느 데스크톱 OS 에서나 도는 것이 목표이며, **첫 기준은 macOS** 다. (iOS/macOS 빌드에 Xcode 가 필요하므로 여기서 시작)
- 소스 프로젝트는 사용자의 **vanilla.js 엔진**으로 만든 게임, 서버, 일반 애플리케이션이다.
- 주요 빌드 툴체인은 **Capacitor**(Android, iOS)와 **Electron**(macOS, Windows, Linux)이다.
- Unity, SteamOS 는 **추후 확장** 대상이며 현재 범위에 포함하지 않는다. 단, 플랫폼/툴체인을 추가할 수 있는 구조는 염두에 둔다.
- **기본부터 하나씩.** 모든 플랫폼의 모든 옵션을 미리 만들지 않는다. 기본 동작을 먼저 만들고 필요할 때 옵션을 하나씩 늘린다.
- **Jenkins 처럼 웹에서 진행 단계를 볼 수 있어야 한다.** 진행도는 웹 API 로 조회할 수 있고, 서버 주소를 브라우저로 열면 현황(큐, 진행 중 작업의 단계, 로그)이 보인다.
- **빌드는 큐로 쌓이고, 중간에 취소할 수 있다.**
- **상시 실행되는 백그라운드 서버 애플리케이션이다.** 손으로 띄우는 것이 아니라 macOS launchd 에 등록해 로그인 시 자동 시작하고 죽으면 다시 뜬다. (`04-service-install.md`)
- **모든 설정은 Jenkins 처럼 웹 UI 에서 바꾼다.** 설정 항목은 포트(기본 8686)와 워크스페이스 디렉토리(기본 `~/.vanilla-builder/`, 그 안에 프로젝트별 폴더) 둘뿐이다.
- **웹에서 파일을 끌어다 놓아 수동으로도 빌드를 걸 수 있어야 한다.** AI 가 API 로 보내는 것과 사람이 웹으로 올리는 것 둘 다 지원한다.
- 모든 요청은 `docs/` 아래 기획서(md)를 먼저 작성하면서 진행한다.
- 코드 스타일과 작업 방식은 `CLAUDE.md` 를 따른다.

## 3. 기본 흐름

```
[작업 PC (Windows) 의 AI / 스크립트]          [빌드 서버 (macOS)]
      │  1. 프로젝트 + 빌드 명세 전송  ─────────▶  수신, 작업 디렉토리에 전개, 작업(Job) 생성
      │                                            │
      │  2. 진행 상태 / 로그 조회      ◀────────▶  명세의 대상 플랫폼별로 빌드 실행
      │                                            │
      │  3. 완료 확인 후 산출물 다운로드 ◀────────  산출물을 artifacts/ 에 보관, URL 제공
```

## 4. 플랫폼별 툴체인 (현재 범위)

| 대상 플랫폼 | 툴체인 | 예상 산출물 | 우선순위 |
|---|---|---|---|
| iOS | Capacitor + Xcode | .ipa (서명 설정 필요) | 1 |
| macOS | Electron + electron-builder | .dmg 또는 .app zip | 1 |
| Android | Capacitor + Android SDK/Gradle | .apk 또는 .aab | 2 |
| Windows | Electron + electron-builder (macOS 에서 크로스 빌드) | .exe 설치 파일 또는 portable zip | 2 |
| Linux | Electron + electron-builder (macOS 에서 크로스 빌드) | .AppImage 또는 .deb | 2 |
| Web | 정적 파일 그대로 (또는 프로젝트 자체 번들 스크립트) | 정적 사이트 디렉토리 zip | 2 |

서버 호스트(macOS)에 필요한 사전 설치물: Node.js, Xcode + Command Line Tools, Android SDK(Java 포함), CocoaPods. 세부 항목은 세부 기획에서 확정한다.

## 5. 가정 (확인 전까지 임시)

- 서버 런타임은 **Node.js** 이며, 프로젝트명(vanilla)과 `CLAUDE.md` 의 스타일 규칙(`#` private 멤버, `System.` 접두사)으로 보아 **외부 프레임워크 없이** 내장 모듈(`http`, `fs`, `child_process` 등)로 구현한다.
- 프로젝트 전달 형식은 **zip 하나**를 기본으로 한다. (개별 파일 전송은 필요해지면 추가)
- 빌드 명세 파일은 **JSON** 이며, 형식은 `01-build-spec.md` 에서 정한다.
- 한 번의 전송으로 여러 대상 플랫폼을 빌드할 수 있다. (명세의 targets 목록)
- 서버가 받는 것은 프로젝트의 **웹 빌드 결과물**(프로젝트에서 `npm run build` 로 만든 `build/web`)과 명세다. 소스 전체가 아니다. 이유는 `03-build-runner.md` 1절.
- "서버" 유형 프로젝트의 산출물은 실행 가능한 Node 프로젝트 디렉토리 zip 이다. (Electron/Capacitor 대상 아님)

## 6. 미확정 질문

- 서버가 받는 입력이 웹 빌드 결과물(`build/web`)인지 소스 전체인지. 가정은 웹 빌드 결과물 (`03-build-runner.md` 1절)
- iPhone 에 설치하는 경로. 작업 PC 가 Windows 라 `.ipa` 를 직접 넣기 어렵고, 기존 흐름은 TestFlight 업로드였다. 업로드 단계 추가 여부 (`03-build-runner.md` 5절)
